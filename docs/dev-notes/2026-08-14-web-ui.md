# Design: Web UI + Deployed Hosting — 2026-08-14

## §1 Job Statement

Let a small, named group of trusted people (the owner plus a couple of close others) each track their own budget through a website, without losing the CLI as a way to use the same data.

## §2 Context and Constraints

- The domain layer (`src/domain/**`), storage layer (`src/storage/jsonStore.ts`), and CLI command handlers (`src/cli/commands/*.ts`) are already built, merged, and reviewed (issues #3 and #6, PRs #4 and #7). The command handlers are already decoupled from the CLI's I/O wrapper — each is a plain `(filePath, options) => Result` function that does its own `loadStore`/`saveStore`. This is the load-bearing fact for this design: a web API can call the exact same handler functions the CLI calls, with no logic fork.
- Current storage is a single JSON file, no user concept — `--file`/`BUDGET_FILE`/`./budget.json`, one file, one implicit owner.
- Scale target is explicitly small: the owner plus "a couple of close others." Not a public product, no self-serve signup, no expectation of growth beyond a handful of named people.
- User has decided (this session): auth is simple username+password (not OAuth), and this phase includes deploying to a live URL now (not local-only).
- `.jome/coverage.json` has `core: ["src/domain/**/*.ts"]` and `enforce: true` — the domain purity/coverage bar stays scoped to domain code; new server/web code is reviewed but not held to the 95% core bar (consistent with how `src/cli/**`/`src/storage/**` were treated in issue #6).

## §3 Decisions & Tradeoffs (READ FIRST)

| Decision | Short-term (now) | Long-term target | Don't-lose-this |
|---|---|---|---|
| **Storage backend** | One JSON file per user (`data/<username>.json`), reusing `loadStore`/`saveStore` from `src/storage/jsonStore.ts` almost unchanged — only the path resolution changes, from CLI flags to a server-computed path. | Swap to a real DB (e.g. SQLite) only if concurrent-write or multi-device durability actually becomes a problem (tracked: budget-tracker#9). | **Invariant:** `PersistedStore`'s shape and the `loadStore`/`saveStore` function signatures stay stable regardless of what's behind them. **Seam:** the storage module's exported interface — swapping the backing implementation must never require changing callers (command handlers, API routes). |
| **Auth mechanism** | Username+password, manually provisioned (you edit a small credentials list, bcrypt-hashed passwords, no signup flow). Session identity carried in a signed, http-only cookie (stateless — no server-side session store, survives restarts/redeploys). | Could add OAuth (e.g. Google) or self-serve signup later if the user list ever needs to grow beyond people you personally add. | **Invariant:** every authenticated request resolves to exactly one username server-side, and all data access is scoped by that username — no endpoint ever accepts a client-supplied user identifier for data access. **Seam:** a single `authenticate` middleware that resolves `req.username`; swapping the auth provider only touches that middleware, never the route handlers or storage layer. |
| **Hosting/deploy target** | Fly.io: single Docker container, one persistent volume mounted at the `data/` directory, deployed now to a live `*.fly.dev` URL. | Could move to any Docker-capable host, or split frontend/backend across hosts, if scale or cost ever demanded it — not expected at this scale. | **Invariant:** the app is a single container with no host-specific code baked into the app itself — all host config lives in `fly.toml`/Dockerfile, not in application source. **Seam:** the Dockerfile + documented volume mount path is the only host-coupling; redeploying elsewhere means writing new host config, not touching app code. |
| **Frontend/backend coupling** | One Express server serves both the built static frontend (Vite + React) and the JSON API (`/api/**`) from a single process — one container, one deploy, no CORS. | Could split into a separately-hosted static frontend (CDN) and API backend if traffic ever justified it. | **Invariant:** the frontend only ever talks to the backend through the versioned `/api/**` JSON contract — it never reads server files or storage directly. **Seam:** that API boundary is what would let frontend and backend separate later without a rewrite. |
| **Business-logic reuse** | The web API's route handlers call the same `addTransaction`/`removeTransaction`/`listTransactions`/`setLimit`/`getStatus`/`getSummary` functions from `src/cli/commands/*.ts` that the CLI already calls — just with a server-resolved `filePath` instead of a CLI-resolved one. | Unchanged — this is the design's core strength, not a temporary shortcut. | **Invariant:** CLI and web API are two thin I/O adapters over one shared command-handler layer; business logic (validation, money/date rules, budget math) never forks between them. **Seam:** `src/cli/commands/*.ts`'s exported handler functions are that shared layer. |

## §4 Alternatives Considered

- **Next.js (or another full-stack framework) instead of Express + Vite React** — rejected for now. Would mean re-hosting the API as framework-specific routes and adopting a much heavier build/routing system than a handful of REST endpoints need. Express keeps the CLI-handler-reuse story trivial (plain function calls, no framework-specific request/response shape to adapt to); Vite+React keeps the frontend simple and framework-agnostic to deploy. Revisit only if this ever needs SSR/SEO — it won't, everything's behind login.
- **A real database (SQLite/Postgres) now instead of per-user JSON files** — rejected for now. Adds a DB dependency, migrations, and connection handling for a use case (a handful of users, low write frequency) that the already-built, already-reviewed atomic JSON-file storage layer comfortably covers. The known gap (concurrent-write lost updates, budget-tracker#9) is a NOTE-level risk at this scale, not a blocker.
- **Google OAuth instead of username+password** — considered and explicitly declined by the user this session in favor of the simpler credential-list approach for 2-3 known people.
- **Separately hosted frontend (e.g. Vercel/Netlify) and backend (Fly.io)** — rejected for now. Doubles the hosting surface and introduces cross-origin cookie handling for a single-container app that doesn't need independent scaling of frontend vs. backend at this size.

## §5 Open Questions

- ~~Who gets an account, and what are their usernames?~~ **Resolved:** just the owner's account for launch. The credentials-list mechanism is built to make adding more people a config edit, not a code change — the "couple of close others" are a fast-follow once the site is live, not part of this build.
- ~~Does the user already have a Fly.io account?~~ **Resolved:** no — account creation + `flyctl` CLI install/auth is a prerequisite manual step (browser signup, can't be done by the agent) before the deploy step of the plan.
- **Custom domain or the default `*.fly.dev` subdomain?** Defaulting to the auto-generated subdomain to start (zero extra setup); a custom domain can be layered on later without touching the app.
- **Does any existing local `~/budget.json` data need to be imported into the hosted version, or does the hosted version start empty?** Defaulting to starting empty — no evidence of real personal data accumulated yet (usage so far has been E2E/demo verification against scratch files). Flag before deploy if this assumption is wrong.
- **Session/cookie lifetime** (e.g. 30-day sliding expiry vs. shorter) — not blocking, can default reasonably at plan/build time.
