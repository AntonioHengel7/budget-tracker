## Locked Decisions (from design §3)

These are frozen. Do not re-decide here.

| Decision | What we're doing |
|---|---|
| Storage backend | One JSON file per user (`data/<username>.json`), reusing `loadStore`/`saveStore` from `src/storage/jsonStore.ts` unchanged — only path resolution is new. |
| Auth mechanism | Username+password, manually provisioned, bcrypt-hashed. Session identity in a signed, http-only, stateless cookie (HMAC-signed, no server-side session store). |
| Hosting/deploy target | Fly.io: single Docker container, one persistent volume mounted at `/data`, deployed to a live `*.fly.dev` URL now. |
| Frontend/backend coupling | One Express server serves both the built static frontend (Vite+React) and the JSON API (`/api/**`) — one container, one deploy, no CORS. |
| Business-logic reuse | Web API route handlers call the exact same `src/cli/commands/*.ts` functions the CLI calls — no logic fork. |
| Launch scope | One account (the owner) at launch. Adding "a couple of close others" is a config edit (append to `AUTH_USERS_JSON`) after launch, not part of this build. |

### `tests/server/session.test.ts`

```ts
import { describe, expect, it } from 'vitest';
import { signSession, verifySession } from '../../src/server/session.js';

describe('session sign/verify', () => {
  const SECRET = 'test-secret';

  it('round-trips a freshly signed token', () => {
    const now = 1_700_000_000;
    const token = signSession('antonio', SECRET, now);
    const result = verifySession(token, SECRET, now + 10);
    expect(result).toEqual({ username: 'antonio' });
  });

  it('rejects a token past its expiry', () => {
    const now = 1_700_000_000;
    const token = signSession('antonio', SECRET, now);
    const THIRTY_ONE_DAYS = 31 * 24 * 60 * 60;
    const result = verifySession(token, SECRET, now + THIRTY_ONE_DAYS);
    expect(result).toBeNull();
  });

  it('rejects a token verified with the wrong secret', () => {
    const token = signSession('antonio', SECRET);
    expect(verifySession(token, 'wrong-secret')).toBeNull();
  });

  it('rejects a tampered username with the original signature reused', () => {
    const now = 1_700_000_000;
    const token = signSession('antonio', SECRET, now);
    const parts = token.split('.');
    const tampered = `mallory.${parts[1]}.${parts[2]}`;
    expect(verifySession(tampered, SECRET, now + 10)).toBeNull();
  });

  it('rejects a malformed token', () => {
    expect(verifySession('not-a-real-token', SECRET)).toBeNull();
    expect(verifySession('', SECRET)).toBeNull();
    expect(verifySession('a.b', SECRET)).toBeNull();
  });
});
```

import { describe, expect, it } from 'vitest';
import bcrypt from 'bcryptjs';
import {
  CredentialsConfigError,
  findCredential,
  loadCredentials,
  verifyPassword,
} from '../../src/server/credentials.js';

describe('loadCredentials', () => {
  it('parses a valid JSON array', () => {
    const json = JSON.stringify([{ username: 'antonio', passwordHash: '$2a$...' }]);
    expect(loadCredentials(json)).toEqual([{ username: 'antonio', passwordHash: '$2a$...' }]);
  });

  it('throws when the env var is unset', () => {
    expect(() => loadCredentials(undefined)).toThrow(CredentialsConfigError);
  });

  it('throws when the env var is empty', () => {
    expect(() => loadCredentials('')).toThrow(CredentialsConfigError);
  });

  it('throws on invalid JSON', () => {
    expect(() => loadCredentials('{not json')).toThrow(CredentialsConfigError);
  });

  it('throws when the JSON is not an array', () => {
    expect(() => loadCredentials('{"username":"a"}')).toThrow(CredentialsConfigError);
  });

  it('throws when an entry is missing username or passwordHash', () => {
    expect(() => loadCredentials(JSON.stringify([{ username: 'a' }]))).toThrow(CredentialsConfigError);
  });
});

describe('findCredential', () => {
  const creds = [
    { username: 'antonio', passwordHash: 'h1' },
    { username: 'friend', passwordHash: 'h2' },
  ];

  it('finds an exact username match', () => {
    expect(findCredential(creds, 'friend')).toEqual({ username: 'friend', passwordHash: 'h2' });
  });

  it('returns undefined for no match, case-sensitively', () => {
    expect(findCredential(creds, 'Antonio')).toBeUndefined();
    expect(findCredential(creds, 'nobody')).toBeUndefined();
  });
});

describe('verifyPassword', () => {
  it('returns true for the correct password against its bcrypt hash', async () => {
    const hash = await bcrypt.hash('correct horse', 4);
    expect(await verifyPassword('correct horse', hash)).toBe(true);
  });

  it('returns false for the wrong password', async () => {
    const hash = await bcrypt.hash('correct horse', 4);
    expect(await verifyPassword('wrong', hash)).toBe(false);
  });
});

## Implementation Steps

### Step 1: Issue A — auth + session foundation

Build `src/server/session.ts` (HMAC-SHA256 signed tokens, format `<username>.<expiry>.<hmac-hex>`, 30-day TTL, `crypto.timingSafeEqual` for the signature check), `src/server/credentials.ts` (`loadCredentials`/`findCredential`/`verifyPassword` wrapping `bcryptjs`), `src/server/paths.ts` (`resolveUserStorePath` with `/^[a-z0-9_-]{1,32}$/` as the only accepted username shape), and `src/server/scripts/hashPassword.ts` (reads `process.argv[2]`, prints a bcrypt hash). File exactly the frozen tests above.

**Gate:** `npm test` green (all three new test files pass, nothing else regresses); `npm run build` compiles cleanly; `npm run gate` still green (domain coverage untouched — this step touches nothing under `src/domain/**`).

### Step 2: Issue B — Express API layer

Extract `todayIsoDate`/`currentPeriod` from `src/cli/index.ts:17-27` into `src/shared/clock.ts`, re-import them in `src/cli/index.ts` (no behavior change — existing CLI/smoke tests must keep passing unmodified, proving the extraction is behavior-preserving). Build `src/server/authMiddleware.ts` (reads the `session` cookie via `cookie-parser`, calls `verifySession`, sets `req.username` or responds 401). Build `src/server/app.ts`'s `createApp(config)`:
- `/healthz` — unauthenticated, always 200 (Fly's health check target).
- `/api/login` (POST) — validates `{ username, password }` are strings, looks up + bcrypt-verifies, signs a session, sets an `HttpOnly`/`SameSite=Lax`/`Secure`-by-default cookie (opt-out via `config.insecureCookies`/`INSECURE_COOKIES` for local dev — not tied to `NODE_ENV`, which is unset by default and would otherwise silently drop `Secure` in production).
- `/api/logout` (POST) — clears the cookie.
- `/api/me` (GET, authed) — echoes `req.username`.
- `/api/transactions` (GET/POST, authed), `/api/transactions/:id` (DELETE, authed), `/api/limits` (PUT, authed), `/api/status` (GET, authed), `/api/summary` (GET, authed) — each resolves `resolveUserStorePath(config.dataDir, req.username)` **from the session-derived `req.username` only, never from `req.body`/`req.query`**, then calls the matching `src/cli/commands/*.ts` handler. `POST /api/transactions` defaults `date` via `todayIsoDate()` when omitted; `/api/status` and `/api/summary` default `period` via `currentPeriod()` when omitted (matching the CLI's own defaulting behavior). `DomainError` maps to HTTP 400 with `{ error: message }` (safe to echo — these messages only ever reflect client input back). `StorageError` is a server-side fault (corrupt file, disk I/O, schema mismatch), never a client mistake — it maps to HTTP 500 with a generic `{ error: "internal server error" }` body; the real message (which otherwise leaks the store's absolute filesystem path and raw OS error text) is logged server-side only. A malformed JSON request body (caught via body-parser's own `err instanceof SyntaxError && err.type === 'entity.parse.failed'` check) maps to 400, not the generic 500 fallback; other body-parser faults (oversized body, bad `content-encoding`) are not covered by that check and still fall through to 500 — a known, non-blocking gap carried forward, not something this step claims to close. Anything else maps to 500 with the same generic body.
- Optional `config.staticDir` — when set, serves it via `express.static` plus a catch-all SPA fallback to `index.html` for any non-`/api` path.

*(Corrected 2026-08-17 — the error-mapping bullet above originally pinned `StorageError`→400 with the raw message, which Socrates's #17 review round 1 found leaked absolute filesystem paths and OS error text to clients; PR #22's fix at commit `a80eaca` implements the corrected mapping shown above.)*

Build `src/server/index.ts` as the env-driven entrypoint (fails fast at boot if `SESSION_SECRET`/`AUTH_USERS_JSON` are missing, rather than failing per-request).

**Gate:** `npm test` green including `tests/server/api.integration.test.ts`; `npm run build` produces `dist/server/index.js`; then a real manual smoke test — run `SESSION_SECRET=x AUTH_USERS_JSON='[{"username":"antonio","passwordHash":"<output of the hash-password script>"}]' PORT=8080 node dist/server/index.js` and confirm `curl localhost:8080/healthz` returns 200 and `curl -i -X POST localhost:8080/api/login -H 'content-type: application/json' -d '{"username":"antonio","password":"<the real password>"}'` returns a `Set-Cookie` header — proving the server actually runs end-to-end, not just that its tests pass.

### Step 3: Issue C — frontend

Scaffold `web/` as an independent Vite+React+TS project. Build `web/src/api.ts` as a thin typed `fetch` client, one function per API route. Build `web/src/pages/Login.tsx` to exactly match the frozen `web/tests/Login.test.tsx` (labeled `Username`/`Password` inputs, a `Log in` button, an `onLoggedIn(username)` callback prop, an `role="alert"` error message on failure). Build `Dashboard.tsx`, `Transactions.tsx`, `Limits.tsx` as the remaining views, and `App.tsx` to gate between `Login` and the rest based on whether `/api/me` currently resolves (no router library — a handful of views behind one auth gate doesn't need one). Configure `vite.config.ts`'s dev-server `proxy` so `npm run dev` in `web/` talks to a locally-running Express server on `:8080` during development.

**Gate:** `cd web && npm test` green (including `Login.test.tsx`); `cd web && npm run build` produces `web/dist/`; then, per this repo's own CLAUDE.md UI-testing rule, a real manual browser check — run the Step 2 server and the Vite dev server together, log in as the owner account in an actual browser, add a transaction, confirm it appears in the list, set a limit, confirm status reflects it. Do not mark this step done on passing tests alone.

### Step 4: Issue D — Docker + Fly.io deploy

Write `Dockerfile` (3-stage: build `web/`, build server `src/`, copy both into a `node:22-alpine` runtime image, `CMD ["node", "dist/server/index.js"]`), `.dockerignore`, and `fly.toml` (port 8080, `/healthz` HTTP check, a `[[mounts]]` volume at `/data`, `DATA_DIR=/data` env, and `[http_service]` set to `auto_stop_machines = "stop"` / `auto_start_machines = true` / `min_machines_running = 0` — with a handful of low-traffic users, the machine should suspend between requests rather than bill 24/7; the volume is the only always-on cost, ~$0.15/mo for the 1GB below).

Manual prerequisites (outside agent control — the user does these): create a Fly.io account, install `flyctl`, `fly auth login`. Then, together: `fly launch --no-deploy` (confirm app name/region against the committed `fly.toml`), `fly volumes create budget_data --size 1` (1GB — more than sufficient for a handful of per-user JSON files), `fly secrets set SESSION_SECRET=$(openssl rand -hex 32) AUTH_USERS_JSON='[{"username":"<owner-username>","passwordHash":"<output of hash-password>"}]'`, `fly deploy`.

**Gate:** `curl https://<app>.fly.dev/healthz` returns 200; log in via the live URL in a real browser and complete one full add-transaction → view-status round trip against the deployed instance (not localhost) before calling this done.
