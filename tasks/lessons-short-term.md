# Lessons — Short Term

Recent patterns (unproven). Format: `[date] PATTERN: what went wrong. RULE: what to do instead.`
Promote to `lessons-long-term.md` after 2+ independent occurrences. Then remove or collapse entries here.

[2026-08-12] PATTERN: tsconfig.json had `rootDir: "."` with `include` spanning both `src/**` and `tests/**` — a single `tsc -p tsconfig.json` build mirrored the whole tree into `dist/`, including compiled test files, and put the CLI entrypoint at `dist/src/cli/index.js` instead of the `dist/cli/index.js` package.json's `bin` field expected. Only caught because the Phase A checklist explicitly ran the built binary, not just `npm test`. RULE: when one tsconfig covers both typecheck-with-tests and production build, split into two configs — a base one (broad include, for editors/vitest/typecheck) and a `tsconfig.build.json` (`rootDir: "src"`, `include: ["src/**/*.ts"]` only, used by the actual `build` script). A green test suite does not prove the built artifact is shaped correctly — always smoke-test the actual build output, not just `tsc --noEmit`.

[2026-08-12] PATTERN: `subMinor()` had a defensive `if (!Number.isSafeInteger(diff))` recheck that coverage-v8 flagged as unreachable — given both operands are already constrained to `[0, MAX_SAFE_INTEGER]` by precondition checks, `a - b` mathematically cannot leave `[MIN_SAFE_INTEGER, MAX_SAFE_INTEGER]`. Nearly wrote a test that could never actually exercise the branch just to satisfy the coverage number. RULE: when a coverage gate flags an uncovered branch, verify whether it's actually reachable before writing a test for it — an "uncovered" branch is sometimes dead code that should be deleted, not padded with a test that can't genuinely trigger it.

[2026-08-18] PATTERN: PR #34's Dockerfile passed typecheck, the full test suite, and a hand-review of every stage/path — but `USER node` (non-root) combined with a Fly volume mounted at `/data` (root-owned by default, not chowned to the image's user) meant every *write* would 500 in production while `/healthz` and reads looked fine; only surfaced because Socrates and Hobbes independently traced `jsonStore.ts`'s actual `mkdir`/`writeFile` calls against the real runtime uid, not just the Dockerfile's shape. Neither `docker build` nor `tsc`/tests would ever catch this — it's a live-filesystem-permission fact, not a type or logic error. RULE: for any container that runs as non-root and writes to a mounted volume, explicitly verify (or write) an ownership-fixup step (e.g. an entrypoint that `chown`s the mount before dropping privilege) — "the image builds and typechecks" is not evidence the runtime user can actually write where the app needs to write.
